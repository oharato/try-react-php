## 1. このステップで身につける「実務レベルの工夫」

ここが **単なるチュートリアルアプリと差別化し、面接官を唸らせる最重要パート** です。

### 1-1. 二重貸出を防ぐ排他制御（トランザクション＋ロック）

2人の社員が同時に同じ機材（例: 検証機A）へ貸出申請・承認を行った場合、素朴な `SELECT` → `UPDATE` だけでは二重貸出が発生します。

Laravel で以下のいずれか（または両方）を実装し、違いを説明できるようにします。

1. **悲観ロック（行ロック）**:
   - `DB::transaction()` 内で `Asset::where('id', $assetId)->lockForUpdate()->firstOrFail()` を実行。
   - ステータスが `Available` でなければ例外（`409 Conflict`）を返す。
2. **楽観ロック（`version` カラム）**:
   - `UPDATE assets SET status = 'loaned', version = version + 1 WHERE id = ? AND version = ?`
   - 更新件数が `0` 件なら他の処理と競合したとみなし `409 Conflict` を返す。

### 1-2. N+1 問題の可視化と解消・EXPLAIN による SQL 検証

1,000件のチケット一覧を取得する API で、あえて一度 N+1 問題を観察してから解消します。

1. チケット一覧（作成者名・担当者名・タグ一覧を含む）を `Ticket::paginate(20)` で取得し、発行される SQL 本数を `DB::enableQueryLog()` で計測する（21本以上発行される）。
2. `Ticket::with(['user', 'assignee', 'tags'])->paginate(20)` に変更し、SQL 本数が数本に減ることを確認する。
3. MySQL コンテナ内で `EXPLAIN` を実行し、Step 1 で貼った複合インデックス `(status, assignee_id, updated_at)` が効いているか（`type`, `key`, `rows`, `Extra`）を確認する。

```bash
docker compose exec mysql mysql -u root -p corpdesk -e "EXPLAIN SELECT * FROM tickets WHERE status = 'open' AND assignee_id = 1 ORDER BY updated_at DESC LIMIT 20;"
```

### 1-3. 社員サポート目線の企画工夫：FAQ サジェスト

ハル研究所の業務内容にある「ユーザー（社員）サポート」に直結する機能です。

- 問い合わせチケット起票画面で、ユーザーが **タイトルを入力している途中（デバウンス 300ms）** に、過去の解決済みチケットや FAQ から関連項目をリアルタイムにサジェスト表示する。
- **狙い**: 社員は問い合わせの返答を待たずに自己解決でき、情シス担当者は定型問い合わせの対応工数を削減できる。

## 2. 実装課題

### 課題 1: 貸出承認時の排他制御と 409 ハンドリング

- `LoanApprovalService` クラスを作成し、`DB::transaction` + `lockForUpdate()`（または `version` チェック）を実装する。
- すでに貸出中の機材に対する承認リクエストには HTTP `409 Conflict` と分かりやすい日本語エラーメッセージを返す。
- React 側で `409` を受け取った際、エラーメッセージを表示しつつ一覧を最新状態に再取得する。

### 課題 2: 問い合わせチケット＆FAQサジェスト

- バックエンド:
  - `GET /api/tickets`（Eager Loading 適用・ステータス/担当者/キーワード絞り込み）
  - `POST /api/tickets` / `POST /api/tickets/{ticket}/comments`
  - `GET /api/faqs/suggest?q=...`（タイトル入力に対する関連FAQ候補を最大5件返却）
- フロントエンド:
  - チケット一覧・詳細・コメント投稿画面
  - 起票フォームでのデバウンス付き FAQ サジェスト表示（カスタムフック `useDebounce` を自作して学ぶ）

### 課題 3: 自動テスト（PHPUnit / Vitest）

- バックエンド（Feature Test）:
  - 一般社員が承認 API を叩くと `403` になるテスト
  - すでに貸出中の機材を承認しようとすると `409` になるテスト（状態整合性テスト）
  - 必須項目不足で `422` バリデーションエラーになるテスト
- フロントエンド（Vitest + React Testing Library）:
  - フォームのバリデーションエラー表示テスト
  - FAQ サジェストが入力に応じて表示されるテスト
